# Harness 运行时核心纪律

> 本文件是从主入口与规则库中抽取的**领域无关运行时纪律**，与具体业务领域无关，供内核编排提示词引用。

## 1. 流程总览

```
Bootstrap 阶段                              PM 调度阶段
──────────────                              ──────────
.harness/scripts/init_task.py               切换 PM 身份（角色定义由 Harness Kit 内核提供）
    ↓                                       ↓
人机协作打磨 proposal.md                     /hk-propose
（消歧义、定 scope、选 profile）              BA → SA → RR → 审批 1
    ↓                                       ↓
人工确认 proposal 定稿                        /hk-apply
    ↓                                       Dev → CR → TE → 审批 2
交接 PM                                     ↓
                                            /hk-archive → DONE
```

- 新工程首次使用先 `/hk-init` 初始化（探测子工程、生成配置 / build.json、人机协作补齐编译启动命令并实跑验证、代码索引）；之后每任务仅需走 Bootstrap。
- Bootstrap 只编辑 `.harness/deliverables/<任务名>/proposal.md`，不碰源码。
- 简单 bug 修复可走 Fix 直通 `/hk-fix <任务名> <一句话描述>`，跳过 propose 文档审批（详见第 5 节质量门）。

## 2. Bootstrap / Propose 阶段硬红线（只读保护）

- **禁止修改 `services/` 下全部子工程（后端 / 前端 / APP 端…，新增端自动纳入）与 `e2e/` 下的任何源码。**
- 此阶段仅允许写入 `.harness/deliverables/<任务名>/*.md`（提案、需求、设计文档）。
- 源码改动只能由 `/hk-apply` 触发的 developer 角色在 TDD 流程下完成。

## 3. 澄清义务与任务分派

- **PM 澄清义务**：遇到范围/口径/验收模糊时，必须向人反问澄清；**禁止 AI 自行"合理补全"后继续推进**。
- **所有任务由 PM 角色拆解后分派**，Worker（BA/SA/RR/Dev/CR/TE）不自行认领任务。
- **制品边界**：下游角色绝对不能修改上游制品；发现上游产出有问题，只能提出阻塞项，由 PM 正式打回。
- **PM 不做专业判断**：PM 只做调度，不给任何技术建议或产品建议，不替其他角色做专业判断。

## 4. Worker 汇报与流转纪律

- 每个阶段必须产出对应阶段的文档后才能流转；文档末尾必须有明确结论 `## 结论`：**PASS 或 BLOCK**（合法结论仅此两者，BLOCK 子类型在结论行括号注明）。
- BLOCK 时必须说明具体原因、修复建议、以及建议打回到哪个阶段/角色。
- Worker 收工汇报格式（PM 读取并转发心跳）：`<产出文件> ## 结论 <PASS|BLOCK>`。
- 任何"完成/已修复/已通过"的表述，必须附带证据——命令 + 关键输出；禁止口头汇报。
- 任何 FAIL 出现后禁止盲目试改；按顺序：读错误 → 稳定复现 → 对照 diff → 定位边界 → 单一假设 → 最小改动验证。同一问题连续 3 次修复未通过 → 停止堆补丁，升级为阻塞项交由人决策。
- **审批材料必须可见可点**：审批 1 / 审批 2 / 质量门前，先发一条普通可见消息（不是 reasoning），用 Markdown 链接列出本轮产物（工作区相对路径）；ask_user_question 的 question 也要带材料链接。`present` 卡片在本轮结束后才出现，不能替代等待回答前的链接；reasoning 不算展示。
- **PM 心跳纪律**：PM 在每个关键锚点（Profile 识别 / 文档就位 / Worker 开工 / 脚本事件 / Worker 收工 / 异常回退）必须立刻输出一行心跳，禁止连续静默跨越多个阶段。

## 5. 质量门人裁决纪律（Fix 直通）

- **无默认值、强制人裁决**：`/hk-fix` 流程中，Dev 开工**前**，PM 按 `bugfix.md`「质量门」表评估复杂度并给出建议，**停下交人裁决** `--full` / `轻量`。
- 三种做法属违规：① 未提问就按轻量继续；② 问了没等人答就往下走；③ 裁决 `--full` 却跳过 CR/TE。
- **裁决值必须写入本轮 `## R<N>` 段的 `**人裁决**` 行**，归档预检强制校验（缺则 FAIL），并校验记录与执行的一致性（裁决 `--full` 时 code-review.md / test-report.md 必须本轮真实落地）。
- 裁决 `轻量` = 只 Dev + 验证（build-test + verify.py）；裁决 `--full` = 才走 CR → TE。调用时预声明 `--full` / `--light` 可跳过提问，但仍须如实登记。
- **裁决后立即改写看板**：PM 须 `update_board.py <任务> --profile fix-full`（走 CR→TE）或 `--profile fix-light`（轻量，链上 CR/TE 标 `—`），不留裸 `fix` 过渡态。
- **RR 的 PASS 不等于自动放行**：RR（就绪评审）PASS 后 PM 必须暂停呈报，人显式执行 `/hk-apply` 才能进入开发。

## 6. 归档规则要点（/hk-archive）

- **增量追加**：本轮增量内容以 `## R<N>` 段**追加**到 `.harness/deliverables/_archive/<任务>/` 对应文件（不整目录快照）。
- **rounds.md**：本轮摘要追加到归档目录的 `rounds.md`。
- **清空活目录**：归档后**清空**活目录 `deliverables/<任务>/`；重开默认 bugfix 轻量文档集，从归档回填活目录，支持 reopen 新轮次。
- **Spec Merge**：把验收能力并入 `.harness/specs/`；只落**最终生效**行为，被反转的中间契约不进 spec（旧契约用 REMOVED 退役，编号不复用）。
- **Memory Merge**：把踩坑经验并入 `.harness/memory/`；CR/TE 只在交付物中提供草稿，由 PM 归档时转为正式条目。
- Fix 直通收尾：`round` 文档归档**必选**；`spec` 合并（缺 requirements.md → N/A 跳过）与 `submodule` 代码合入**可选**。

## 7. 三步验证底线（不可协商）

每次代码修改完成后，必须依次完成并全部通过：

1. **编译验证**：执行各子工程 `.harness/build.json` 的 `compile` 命令。
2. **启动验证**：执行各子工程 `.harness/build.json` 的 `start` 命令，服务正常启动；未声明 `start-ok` 判据 = 未验证 ≠ 通过。
3. **事后验证（硬门禁）**：运行 `.harness/scripts/verify.py`，全部 PASS。

- ❌ 禁止以"特殊情况""历史遗留""只改了前端"等理由跳过任何验证步骤。
- ❌ 禁止在验证未通过时继续推进流程（CR、合并或归档）。

## 8. 证据与否定性结论纪律（摘要）

- **否定性结论必须配覆盖面论证**：`grep` 无命中 ≠ 不存在；断言"不存在 X"前须列同义词族/变体逐条判定，只报 `NO_HITS` 不构成证据。
- **禁止自证循环**：自检断言的判据不得取自被检对象自身的产出，必须来自独立源（改动前基线、独立扫描器等）。
- **「不可复现」必须量化**：给结构性论证 + 已尝试手段清单 + 可观测半边的独立闭环证据，且仍不得计 PASS，须交人工裁决。
- **敏感字面量纪律**：凭据/密钥/令牌禁止写进任何说明性制品（报告、日志、提交信息），用脱敏 token 指代、只在结论中给计数；发现即上报 PM 直接脱敏。

## 9. 子代理等待纪律（2026-11-19 定，针对轮询浪费）

- **优先不等待**：派发子代理后结束当前回合，靠子代理完成通知继续；只有必须串行依赖时才阻塞等待。
- **必须等待时只等一次**：`wait_agent` 的 `timeout_ms` 用足够长的值（不超过 3600000），不要用 5 分钟短超时反复轮询。同一批子代理只等一次。
- **禁止进度盘问**：不要用 `send_message` 问「进度如何/完成了吗」；子代理完成会自动通知。只有需要补充信息时才发消息。
- **超时后的动作**：先做不依赖该子代理的独立工作，或向人汇报当前状态；不得连续重新 poll。
- **等待期间不更新看板/不重复派发**：看板和心跳只在阶段边界或子代理真正返回后更新。

> 实测（2026-11-19 三个大任务）：`wait_agent` 29–39 次全部超时，父会话 11%–18% 的 Token 花在超时轮询上，墙钟时间被拉长数小时。

## 10. 上下文读取纪律（2026-11-19 定，控制 Token）

- **先读 handoff**：任务目录存在 `handoff.md` 时，先读它；只按其中「读取清单」取章节，**不整份重读** requirements / design / spec。
- **大文件先定位**：超过约 300 行的文件，先用 `grep` 找符号/标题，再用 `read` 的 `offset`/`limit` 读目标段；禁止无差别整文件读取。
- **同一文件同一轮只读一次**：修改后用 `git diff` 或局部读取验证，不重新通读全文。
- **工具输出只留结论**：测试/构建日志用 `tail`/`grep` 取失败摘要；不要把整段日志或整份报告贴回上下文。
- **交接摘要代替全文转发**：PM 在 `handoff.md` 中写本轮决策、AC、读取清单和风险；Worker 不通过复制上游全文来获得上下文。
- **子代理输入自包含但不冗长**：派发消息给任务背景、产出路径、读写范围、handoff 路径和必要章节，不内嵌整份上游文档。
